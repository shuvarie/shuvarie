# AGENTS.md

Shuvarie (シュヴァリエ, "chevalier") is a terminal-based AI agent coding tool built in Rust. This file orients AI agents (and humans) to the codebase, conventions, and intended architecture so that changes stay consistent.

## Workspace crates

- `./` (binary `shuvarie`) — TUI rendering, event loop, input handling, channel wiring. **No business logic lives here.** Renders state produced by `shuvarie-core`.
- `./crates/core/` (`shuvarie-core`) — App state, config + connections loading, the async core task that orchestrates LLM and database work, and the twelve agent tools (`tools.rs`: read/write/edit files, run commands, list dirs, grep, glob, `lsp`, `webfetch`, `question` — question types + `QuestionGate` in `question.rs`; `apply_patch.rs`: multi-file patch envelope; `todos.rs`: the `todo` tool + `TodoState` — derived state replayed from persisted `todo` tool-call records at every send, surfaced as a styled list in the chat pane and done/total counts in the sidebar). Owns the domain `Session`/`Event`/`Command` logic and persists through `shuvarie-db`. Depends on `selune`, `shuvarie-db`, `shuvarie-llm`, and `shuvarie-lsp` (`connections.rs` holds a provider `kind` id resolved against the `selune` catalog; `catalog.rs` is the pricing/context/embedding helper layer; tools implement `rig::tool::Tool` (re-exported via `shuvarie_llm`); the core task owns an `shuvarie_lsp::LspManager`).
- `./vendor/selune/` (`selune`, git submodule) — The uniform source of provider + model info, in the Catwalk format: `Provider`/`Model`/`ModelOptions`/`ProviderType` (wire types), `TokenUsage`-independent data (`context_window`, `cost_per_1m_*`), a blocking `Client` that fetches a hosted catalog JSON (`CATALOG_URL` / `DEFAULT_URL`) plus `embedded::all()` (offline configs). Provider identity is a catalog `id` string (e.g. `anthropic`, `openai`, `togetherai`). `shuvarie-core::catalog` loads providers (fetch with embedded fallback) and derives pricing/context/requires-key/endpoint behavior from them.
- `./crates/llm/` (`shuvarie-llm`) — Thin wrapper over `rig`: `ProviderClient` builder, model listing (via rig's `ModelListingClient`), streaming agent chat (`stream` — multi-turn with tools; `run_worker` — single-shot worker agent loop), and the `into_dynamic` helper that wraps a typed `rig::tool::Tool` as a `DynamicTool`. The tool surface is re-exported from rig (`Tool`, `ToolOutput`, `ToolContext`, `ToolExecutionError`, `ToolErrorKind`, `DynamicTool`, `PortableDynamicTool`, `ToolSet`, `ToolDefinition`); `shuvarie-core`'s file tools implement `rig::tool::Tool` and report a `FileChange` (`Edit { path, diff, original, new }`, `Write { path, content, original }`, or `Patch { files }` for multi-file patches) via `ToolContext::insert_result`, which a `FileChangeHook` (a rig `AgentHook`) captures and forwards into the emitted `StreamItem::ToolResult`. `WorkerAgent` (an agent-as-tool whose `call` runs its own `stream_chat` loop over a narrowed tool set, forwarding its tool activity through an mpsc channel merged into the manager stream), `ChatMsg`/`Role` message types, `StreamItem` (with `Delta`/`Reasoning`/`ToolStart`/`ToolResult`/`WorkerStart`/`WorkerResult`/`Done`/`Error` — reasoning captured from rig's `StreamedAssistantContent::Reasoning`/`ReasoningDelta`), and the shared `TokenUsage`/`Model` types (re-exported as `rig::completion::Usage` and `rig::model::Model`). Depends on `selune` (via `ProviderType`) for provider identity; no pricing/estimation lives here. No TUI concerns.
- `./crates/db/` (`shuvarie-db`) — Persistence layer: Toasty models (`Session`, `Message`), the `Store` wrapper over `toasty::Db` (Turso embedded SQLite via `toasty-driver-turso`), embedded schema migrations, and a `migrate` bin (toasty-cli) for managing them. No TUI concerns.
- `./crates/highlight/` (`shuvarie-highlight`) — Markdown + code highlighting for the chat pane. `md.rs` walks pulldown-cmark events into styled ratatui `Line`s (paragraphs, lists, quotes, tables, code fences); `syntax.rs` highlights fenced code via syntect with a programmatic heraldic theme (regex-fancy, no onig); `diff.rs` is a custom ` ```diff ` renderer (`+` SUCCESS, `-` ERROR, `@@` ACCENT); `theme.rs` holds the syntax color palette (a heraldic complement to `src/tui/theme.rs`). Exposes `render(text) -> Vec<Line<'static>>` and `plain(text)`. Emits unwrapped lines — wrapping/line-counting stays with the `Paragraph` in the TUI. No TUI concerns.
- `./crates/lsp/` (`shuvarie-lsp`) — Language Server Protocol client lifecycle. `config.rs` defines `LspConfig`/`LspServerSpec` (serde, `lsp` section of `config.kdl`); `registry.rs` holds the built-in per-language server table (`rust-analyzer`, `gopls`, `clangd`, `pyright`, `typescript-language-server`, `zls`, `lua-language-server`, `solargraph`) + `merge_overrides` (user `lsp` `server <lang>` overrides win field-by-field) + `probe` (PATH lookup); `server.rs` spawns one LSP server as a `tokio::process::Command` child, wires its stdout/stdin through `tokio-util::compat` into `async_lsp::MainLoop::run_buffered`, and exposes `did_open`/`did_change`/`did_close`/`shutdown`/`kill`; `manager.rs` (`LspManager`, wrapped `Arc<Mutex<..>>` as `SharedManager` in `shuvarie-core::lsp_manager`) owns the active servers, dispatches `start`/`stop`/`restart`/`list`/`analyze`, auto-starts on `on_file_change` (gated by the `lsp` `enabled` flag + per-spec `auto-start`), and collects `publishDiagnostics` into a per-path `DiagnosticMap` pumped by the core task. Depends on `async-lsp` (`omni-trait`/`client-monitor`/`tracing`), `lsp-types`, `tokio`/`tokio-util` (compat), `tower`. No TUI concerns.

When adding a feature: put domain logic in `shuvarie-core`, provider/model data + pricing in `selune` (via `shuvarie-core::catalog`), LLM/SDK glue in `shuvarie-llm`, storage/ORM glue in `shuvarie-db`, markdown/code highlighting in `shuvarie-highlight`, LSP client lifecycle in `shuvarie-lsp`, and only rendering + input dispatch in the root binary.

## Architecture

### The Elm Architecture (TEA) — hierarchical

The TUI follows `map_event → message → update → return`:

- `map_event` (pure, no side effects): maps a terminal `Event` (or an async channel message) to a message (e.g. `AppMessage`). Takes `&self`/`&App` only — never mutates.
- `update` (mutates the model): consumes a message and may produce an effect (e.g. `AppEffect::Quit`) or an effect for the parent.
- `view(&self, frame: &mut Frame<'_>, area: Rect)`: draws current state. A TEA model is **not** required to implement `ratatui::Widget`; the dedicated `view` method takes a `Frame` + `Rect` and may compose multiple widgets, so it is not limited to a single widget's render contract. No side effects in `view`.

The root `App` composes **submodels**, each following the same TEA shape with its own message enum, `map_event`, `update`, and `view`. Submodels own their state and logic; the parent dispatches events, forwards grouped messages, handles routing, and processes core events:

```
App (parent)
├── SessionScreen        — SessionMessage, map_event(&self), update → Option<SessionEffect>, view(&self)
│   └── chat::Chat       — ChatMessage, update, view(&self) — the chat history pane
│       └── turns[]      — Vec<Block> per turn; Block enum aggregates per-block TEA models
├── CommandMenu          — CommandMenuMessage, map_event, update → Option<CommandMenuEffect>, view(&self)
├── AddProviderForm     — AddProviderMessage, map_event(key, stage), update → AddProviderOutcome, view(&self)
├── ModelPicker         — ModelPickerMessage, map_event, update → Option<ModelPickerEffect>, view(&self)
├── Welcome             — WelcomeMessage, map_event, (no update — parent handles directly), view(&self)
└── ConfirmQuit         — ConfirmQuitMessage, map_event, (no update — parent handles directly), view(&self)
```

When creating a new component, it's usually expected to be a TEA model, unless such an architecture doesn't fit the requirement.

There should be a `new` and a `view` method, and a `update` method when data updating is required.

**Message grouping**: `AppMessage` wraps submodel messages — `Session(SessionMessage)`, `AddProvider(AddProviderMessage)`, `ModelPicker(ModelPickerMessage)`, `CommandMenu(CommandMenuMessage)`, `Welcome(WelcomeMessage)`, `SessionPicker(SessionPickerMessage)`, `HistorySearch(HistorySearchMessage)` — plus parent-only variants (`OpenCommandMenu`, `RequestQuit`, `ConfirmQuit`, `CancelQuit`, `Resized { rows, cols }`, `ConfigSaved`, `ConfigError`, `ModelsLoaded`, `ModelsError`, `SessionsLoaded`, `SessionLoaded`, `SessionCreated`, `SessionDeleted`, `SessionError`). `SessionMessage` in turn groups chat data as `Chat(ChatMessage)` alongside session-level variants (`Text`, `CancelRequested`, `ShowError`/`ClearError`, `UsageUpdate`, `UpdateConfig`, `QuestionAsked`, `Question`, `Slash`, `Reset`, `Loaded`, `TurnReverted`, `TurnRestored`). The TUI `Event` enum (`src/tui/event.rs`) unifies terminal and core inputs: `Event::Terminal(termina::Event)` and `Event::Core(shuvarie_core::Event)`. `App::map_event(ev, &app)` matches on `Event` — terminal events are dispatched overlay-aware then route-aware (below), while core events are mapped to `AppMessage` directly: chat-data events (`TokenReceived`, `ReasoningReceived`, `ContextLoaded`, `ToolStarted`, `ToolFinished`, `ToolOutput`, `WorkerStarted`, `WorkerFinished`, `StreamDone`, `StreamError`, `StreamCancelled`, `LspDiagnostics`) wrap into `Session(Chat(...))`, usage events (`UsageUpdate`) wrap into `Session(UsageUpdate)`, session events (`SessionLoaded`, `SessionCreated`, `SessionDeleted`, `SessionsLoaded`, `SessionError`) stay at the parent level (they populate the chat view and the SessionPicker), search events (`SearchResults`, `SearchError`) wrap into `HistorySearch(...)`, `Pong` closes the command menu, and `ConfigSaved`/`ConfigError`/`ModelsLoaded`/`ModelsError` stay at the parent level (the parent reloads config from disk on `ConfigSaved` so submodels see fresh provider data, and auto-selects a model on `ModelsLoaded`). `Resized` is sent from the `tui.rs` event loop when the terminal size changes and dispatched in `App::update` to the open overlay's `Resize { viewport_height }` submessage (computed from the popup rect + overlay block inner layout) so the overlay can recompute its scroll offset.

**Event dispatch flow** (`App::map_event`, overlay-aware, then route-aware):

1. `Event::Terminal` — if an overlay is open → route to that overlay's `map_event` (CommandMenu, AddProviderForm, ModelPicker, Welcome, ConfirmQuit, SessionPicker, HistorySearch).
2. Else `Ctrl+C` → `RequestQuit` (opens ConfirmQuit overlay; cancels the stream first if the session is streaming).
3. Else `Ctrl+M` → `OpenCommandMenu` (parent-level global keybind).
4. Else `Ctrl+R` → opens the `HistorySearch` overlay.
5. Else route to the session screen's `map_event`.
6. `Event::Core` — mapped to `AppMessage` directly (see Message grouping above).

**Update forwarding**: `App::update` matches `AppMessage` — parent-only variants are handled in-place; submodel variants are forwarded to `submodel.update(msg, &self.ctx)`. `CommandMenu::update` returns `Option<CommandAction>` (the shared registry type from `src/tui/commands.rs`); the parent routes it through `App::run_command(action)`, which performs the parent-level actions (opening the ModelPicker overlay, opening the AddProviderForm, opening the SessionPicker / starting a fresh session, sending `UndoLastTurn`/`Redo`/`Replay`/`Resume` to core, or quitting — returning `Some(AppEffect::Quit)` to `update`) and is also used by `SessionEffect::RunCommand` from the slash menu. `SessionScreen::update` returns `Option<SessionEffect>` (`SendMessage` → if the screen has no session yet, `StartSession` first, then send command to core; `RunCommand` → execute a slash command picked from the inline tooltip) and forwards `Chat(ChatMessage)` into `chat.update(...)` while mirroring the streaming lifecycle onto its busy/status row (`observe_chat`); `SessionScreen::Loaded`/`TurnReverted`/`TurnRestored` update the screen fields + sidebar usage and forward the session into `ChatMessage::Load`/`TurnReverted`/`TurnRestored`. `Chat::update` mutates turns/blocks only — no effects. `AddProviderForm::update` returns `AddProviderOutcome` (`Submit` → add provider + set active + list models; `Cancel` → close or back to kind list). `ModelPicker::update` returns `Option<ModelPickerEffect>` (`Selected` → set active model). `SessionPicker::update` returns `Option<SessionPickerEffect>` (`LoadSession` → resume; `DeleteSession` → delete with a second `Ctrl+D` to confirm; `NewSession` → fresh conversation). `HistorySearch::update` returns `Option<HistorySearchEffect>` (`Open` → show overlay; `Search { query }` → send `Command::SearchHistory`; `LoadSession` → resume the found session).

**`UpdateCtx`** (`src/tui/context.rs`): carries `connections: Connections` and `cmd_tx: Sender<Command>`. Passed by shared reference (`&UpdateCtx`) to submodel `update` calls so they can read provider data and send commands without owning them. The parent owns the `UpdateCtx` and reloads `connections` from disk on `ConfigSaved`.

**Adding a feature**: add a message variant to the relevant submodel's enum (and an effect/return if the parent needs to act), an `update` arm, and `view` logic. Keep side effects out of `map_event` and `view` — send commands via `ctx.send(...)` in `update` only. If a new submodel is needed, add a message enum, `map_event`, `update(&UpdateCtx)`, and `view`, then compose it in `App` and add a grouped `AppMessage` variant.

The `view` method must have an immutable `self` reference (`&self`) as parameter — it never mutates the model.

### Async runtime: Tokio

`main` is `#[tokio::main]`. The TUI loop runs on the main thread using `termina`'s `EventStream` (the `event-stream` feature) so the loop can `tokio::select!` between terminal key events and core events without blocking. All LLM and database work runs on a spawned **core task** (`shuvarie_core::run`). Communication is via `tokio::sync::mpsc` channels:

- TUI → core: commands (e.g. `SendMessage`, `StartSession`, `ListModels`, `AddProvider`, `SetActiveModel`) — `shuvarie_core::Command`.
- Core → TUI: events (e.g. `MessageReceived`, `ReplyError`, `SessionStarted`, `ModelsLoaded`, `ConfigSaved`) — `shuvarie_core::Event` — wrapped in `Event::Core` by the `tui.rs` event loop, mapped to `AppMessage` variants by `App::map_event`, and fed into `update`.

Keep the TUI thread free of `await`s on blocking work; offload any blocking work to the core task (or `spawn_blocking`). The `select!` loop wakes on either a terminal event or a core event, so live updates (model lists, streaming tokens) render without requiring a keypress. All events flow through one draw decision: each wake applies the event (core events are drained as a batch), then a frame is drawn at most once per frame-budget interval (`[ui].frame_rate`, default 60 fps; `0` disables the cap) — when the budget has elapsed the frame draws immediately, otherwise a deadline anchors at `last_draw + budget` and further events coalesce into the pending frame (terminal events included, so scrolling under a token flood draws at most once per budget; when idle the budget has already elapsed, so keys still render immediately). When no event changed state, the loop keeps listening without redrawing.

### Storage: hybrid

- **Config file** (layered priority chain: `$cwd/shuvarie.kdl` → `$cwd/.shuvarie/config.kdl` → global `~/.config/shuvarie/config.kdl`; KDL via `kdl-rs`'s serde feature — `kdl::de::from_str`/`kdl::se::to_string` wrapped in `shuvarie-core::config::kdlserde`, output autoformatted; config structs live in `crates/core/src/config/`): every existing file in the chain is merged layer by layer (`Config::load` → `load_chain`) — per top-level section the highest-priority file defining the section wins wholesale (so a locally-winning partial section resets its other fields to defaults), except `lsp.servers`, which merges key-by-key with the higher-priority spec winning per language; `--config <FILE>` (`cli.rs`) bypasses the chain and loads exactly that file (`Config::load_explicit`, missing file hard-errors) and becomes the target for config saves, while chain mode always saves to the global file. UI preferences (`ui` `frame-rate` — target frames per second for the render loop, default 60; `0` draws every event), the `embedding` settings, the `agent` turn budgets (`max-turns` default `0` = unlimited, `worker-max-turns` default `0` = unlimited), the `context` context-management settings (see Context management below), the `lsp` settings, and the `skills` settings (`dirs` — extra skill directories). No secrets.
  - **Bool polarity note** (kdl-serde quirk): kdl-se drops entries whose value serializes to `Bool(false)`/`Null`, and kdl-de reports absent nested structs' fields as `false`/`Option::None` (serde `#[serde(default)]` never fires one level deep; it does work at the top level). Those two rules cancel out, so default-on flags are stored directly as inverted fields: `disabled` (and `no-auto-start` for LSP specs) — `disabled #true` = off, omitted or `#false` = on; internal state (e.g. `shuvarie_lsp::LspConfig.enabled`) stays positive and is negated only in the repr `From` impls. Non-Option scalars/Vecs/structs at nested level need `deserialize_with = "kdlserde::de_default"` (or the per-field numeric fallbacks in `kdlserde.rs`) — a bare field would hard-error on an omitted value ("invalid type: boolean").
  - `lsp` layout: `lsp { servers { <lang> { command "cmd" extensions ".rs" no-auto-start root-markers } } }` — kdl-serde keys maps by node name, so the old `server "<lang>" { ... }` argument-keyed shape is gone. Core keeps private serde mirror types (`config::LspConfigRepr`/`LspServerSpecRepr`) converted to/from `shuvarie_lsp::LspConfig` via `From` impls; the `shuvarie-lsp` crate stays KDL-free (its `enabled`/`auto_start` stay positive, negated at the repr boundary).
  - `skills`: `disabled` (default off = enabled); `dirs` as bare string args.
  - `connections.kdl` (same module): `active { provider "id" (model "id") (variant "id") }` (block form — a bare `active "provider" "model"` positional form and an `active` block without a `provider` child are parse errors) plus `providers { provider id="..." name="..." { kind "..." api-key "..." base-url "..." } }`. Hand-rolled KDL in `shuvarie-core::config::connections_kdl` (not kdl-serde — the property-form `provider id= name=` isn't expressible there); the legacy `providers { <name> { ... } }` / `active-provider`/`active-model` shape is rejected with an error. Providers are keyed by `id` (any unique string; the TUI AddProvider wizard generates a UUID v4); `name` is the display name and `kind` is the required Selune catalog id (a child node, like `api-key`/`base-url` — omitting it is a parse error). The active state is a `Connections::Active` struct (`provider` + optional `model`/`variant`, stored as `Connections.active: Option<Active>`); `variant` is config-only for now (no model-selection wiring). Keeps secrets out of the database and out of `config.kdl`.
- **Database** (`.shuvarie/data.db` in the working directory — Turso embedded SQLite + Toasty ORM): chat sessions, message history (with positioned reasoning segments + interrupted flag), tool call records (per-message, with file-change JSON + original/new content for undo), and the undo log (DB-backed multi-level redo, survives reload). Sessions are identified by a UUID v7 primary key (`sessions.id` = `uuid::Uuid`, `#[auto(uuid(v7))]`, stored as BLOB); `messages`, `tool_calls`, `undo_logs`, and `message_embeddings` FK it by `session_id`. The `Message`/`ToolCall`/`MessageEmbedding` row ids stay auto-increment `u64`. Provider config stays in the KDL files regardless. When `Store::open` newly creates the `.shuvarie` directory it seeds a `.gitignore` containing `*` in it (only on directory creation — reopening never touches an existing `.gitignore`, and non-`.shuvarie` store paths don't get one).
- **Migrations**: schema is managed with toasty migrations, not `push_schema` (which emits bare `CREATE TABLE` and fails on re-open). Migration files live in `crates/db/toasty/` and are embedded into the binary via `toasty::embed_migrations!`; `Store::open` applies them automatically. Regenerate with `cargo run -p shuvarie-db --bin migrate -- migration generate --name <change>`, then `apply` (or just reopen a store — the embedded set applies pending migrations at open). The `migrate` bin uses an in-memory DB and a programmatically-built `toasty-cli` config pointing at `crates/db/toasty` so it is CWD-independent. `next_seq` uses `MAX(seq)+1` (not row count) so undo/delete doesn't collide.
- **Tool call + reasoning persistence** — each assistant turn's tool calls (name, args, output, ok, worker, file-change JSON, original/new content, duration) are persisted in a `tool_calls` table keyed to the assistant `Message` row (created eagerly on first tool start of the turn, updated on `Done`/`Error`/cancel). Reasoning/thinking is captured from rig's `StreamedAssistantContent::Reasoning`/`ReasoningDelta` as positioned `ReasoningSegment`s (`shuvarie_db::ReasoningSegment { after_tool, text, duration_ms }` — `after_tool` anchors the segment to the number of tool calls completed before the chunk began, so thinking can happen anywhere in the turn, and `duration_ms` spans the segment's first→last chunk), serialized as a JSON array into `messages.reasoning` by `shuvarie-db` (`encode_reasoning`/`parse_reasoning`; legacy plain-text rows load as a single start-anchored segment, and `undo_logs.reasoning` stores the same segment JSON opaquely). On session reload, `Session::from_stored` reconstructs tool records + reasoning segments so the chat pane shows full tool activity and diffs, not just plain text. `interrupted: bool` on `Message` marks turns cancelled by the user or aborted by errors (including the max-turn limit) — the TUI keeps interrupted turns visible (the "Resume" command is offered only when the last assistant message is interrupted).
- **Undo / redo / replay / resume** — `Command::UndoLastTurn` moves the last user+assistant pair + their tool calls into the `undo_log` table and reverts file changes (restoring `original_content` or deleting newly-created files). `Command::Redo` pops the last `undo_log` row, re-inserts messages + tool calls, and re-applies file changes. `Command::Replay` = undo last turn + re-`SendMessage` the last user content as a fresh turn. `Command::Resume` = delete the interrupted assistant message + its tool calls, then re-stream from the last user message (removing the incomplete turn, restarting it). The TUI keeps interrupted turns visible in the chat (partial text + reasoning + completed tool activity; still-running tools with no result are dropped) — the incomplete turn is only removed when rerun via `Replay`/`Resume`. `SendMessage` truncates the session's `undo_log` (a new turn invalidates redo). Undo reverts file changes only from `read`/`write`/`edit`/`list_dir`/`grep` — `run_shell` effects are never reverted.
- **Full-text search** — the schema declares `CREATE INDEX "index_messages_fts" ON "messages" USING fts ("content")` (Turso/Tantivy FTS), and `Store::open`/`open_in_memory` construct the driver with `.experimental_index_method(true)` so that statement is accepted. Searches run through toasty's raw SQL (`toasty::sql::query` with `fts_match`/`fts_score`, `?1`-style numbered placeholders, `column_types` hints for decoding) in `Store::search_messages` — BM25-ranked hits joined with session titles, content returned raw for the TUI to truncate. The FTS index tracks inserts/deletes automatically.
- **Semantic search** — a `message_embeddings` table stores one `vector32` blob per message (raw f32 LE bytes in a `Vec<u8>` BLOB column). Embeddings are written on message append and backfilled at startup (batches of 64) via `Store::upsert_embedding`/`messages_missing_embeddings`; `Store::semantic_search` ranks by `vector_distance_cos(e.vec, ?1)` (bind the blob with `bind_typed(..., db::Type::Blob)`). Deleting a session cascades through Toasty's app-level cascade (required FK `message_id: u64` on `MessageEmbedding` → `Message`, chained from `Session`) — no manual deletes. `Ctrl+R` search is hybrid: FTS results render instantly, then a debounced (300 ms, abort-on-keystroke via `AbortHandle`) query embed runs `semantic_search` and both lists merge by reciprocal rank fusion (`rrf_merge`, k=60) — semantic hits carry `SearchSource::Semantic` (`⌕` tag in the overlay). Embedding config lives in `[embedding]` (provider/model/dimensions; defaults per provider kind, see `shuvarie-core::embeddings`); providers without embedding support (Anthropic/DeepSeek/Groq) degrade to FTS-only.
- **Context management** — the multi-turn agent loop re-sends the full accumulated conversation (preamble + history + every prior tool result) on each model call, so long turns blow up input tokens quadratically. Shuvarie bounds this with three layers: (1) **Tool-output caps** — `read_file` truncates returned text at `[context].tool_output_max_chars` (default 16,000 chars) or `[context].tool_output_max_bytes` (default 50,000 bytes, UTF-8-boundary-safe), whichever caps first, via the shared `truncate.rs` helper (also used by `webfetch`); long lines are capped at 2,000 chars with a suffix plus a `run_shell` hint for reading them exactly; a per-turn `ReadCache` (`tools.rs`) dedupes repeated reads of the same `(path, offset, limit)` and tracks read paths for `write_file`'s read-first overwrite check. (2) **History-budget hook** — `shuvarie-llm`'s `ContextHook` (a rig `AgentHook` in `context_hook.rs`) runs before each model call: it **forecasts** the request's input tokens anchored on the last call's real request-side usage (the `UsageTracker` from rig's `MultiTurnStreamItem::CompletionCall` keeps the most recent call's `total − output`, not a cumulative sum) plus a chars/4 estimate of only what was appended since; with no anchor yet (first call, or a provider that reports no usage) it falls back to chars/4 over the whole request plus the preamble estimate (`ContextBudget.preamble_tokens`). When the forecast crosses the usable budget (`context_length − [context].reserved`, context from `shuvarie-core::catalog::context_length` or `[context].fallback_context_length` default 128K), the hook sends a trimmed copy (`RequestPatch.history`) that keeps the recent tail verbatim within `[context].keep_recent_tokens` and replaces older tool results with recovery-hint stubs (`[elided: <tool> result (N chars) — re-run <tool> if you need it]`; text messages are never dropped or truncated). If even the trimmed request would not fit, the run is stopped **before** the provider call (`CompletionCallAction::Stop`), surfaced as `StreamItem::Overflow`. (3) **Compaction** (`compaction.rs`) — on `Overflow`, the older messages (head) are serialized (tool outputs truncated to 2 KB) and summarized via a single-shot `run_worker` call into a structured Markdown summary (Objective / Important Details / Work State / Next Move / Relevant Files), persisted as a `summary`-flagged `Message` (`Store::append_summary`). `Session.summary_seq` tracks the most recent summary; `Session::history_for_send` replaces everything before it with the summary on subsequent turns. The TUI renders a `◈ summary of earlier conversation` marker above the summary message. After a successful compaction the run loop **auto-continues** (matching OpenCode): it reports the stream outcome over a `stream_done` channel, and on `Overflowed { compacted: true }` replays the last user message via `resume_last_turn` (the same path as the manual `Resume` command), bounded by a 3-retry guard (`overflow_retries`) so a session that can't be compacted small enough stops with an error instead of looping. Config: `[context]` (`disabled` inverted key, default on; `reserved` default 20,000; `keep_recent_tokens` default 20,000; `tool_output_max_chars` default 16,000; `tool_output_max_bytes` default 50,000; `fallback_context_length` default 128,000).

### LLM providers

All provider access goes through `rig` in `shuvarie-llm`. Supported providers, via `rig`'s built-in clients:

- **OpenAI-compatible** — OpenAI proper plus any OpenAI-compatible endpoint (OpenRouter, local `llama.cpp` server, etc.).
- **Anthropic** — Claude models.
- **Gemini** — Google models.
- **Ollama** — local models, no API key required (good for offline development).
- **Ollama Cloud** — Ollama's hosted cloud service (`https://ollama.com`, Bearer API key from <https://ollama.com/settings/keys>); same Ollama API as local, so it reuses rig's `ollama` client with a key + base URL.

`shuvarie-llm` exposes a `Provider` enum and a model-listing/streaming API; the root binary never calls `rig` directly.

### Rendering stack

`ratatui` with the `termina` backend feature (`default-features = false`, curated feature set in the root `Cargo.toml`). Alternate-screen enter/exit is handled manually via CSI escapes in `src/tui/escape.rs` — do not switch to a backend-managed alt-screen toggle without reason. The Kitty keyboard protocol is enabled on init (`ENABLE_KITTY_KEYBOARD` — `DISAMBIGUATE_ESCAPE_CODES | REPORT_ALTERNATE_KEYS`) so modified keys like `Shift+Enter` carry their modifier bits (parsed via termina's `parse_csi_u_encoded_key_code`); terminals that don't support it ignore the sequence and the app degrades gracefully (the newline binding is inert, `Enter` still submits). Button-event mouse tracking (`ENABLE_MOUSE`, mode 1002) with SGR extended coordinates (`ENABLE_SGR_MOUSE`, mode 1006) is also enabled on init and popped on deinit — termina parses the reports into `Event::Mouse` (`MouseEvent { kind, column, row }`), which `App::map_event` routes to `SessionMessage::Click`/`Wheel` only when no overlay is open; unsupported terminals ignore the sequences. The flags are popped on deinit.

### UI design — modern, borderless, muted

The visual style is defined in `src/tui/theme.rs` and used by all submodel `view` methods. Follow these principles when adding or modifying UI:

**Color palette** — all colors are `Color::Rgb` (true color), a medieval/heraldic theme: dark iron-and-stone backgrounds, antique gold accent (heraldic *or*), parchment-cream text, and weathered tinctures for semantics. Never use pure RGB primaries (`Color::Red`, `Color::Green`, etc.) or the `Stylize` shorthand colors (`.red()`, `.cyan()`, etc.) in UI code — import from `theme` instead. The palette:

| Constant | Role |
| --- | --- |
| `BG` | App background (forged iron black) |
| `SURFACE` | Unfocused pane/section background (castle stone) |
| `SURFACE_FOCUSED` | Focused pane background (polished iron) |
| `OVERLAY` | Popup/modal background (weathered stone) |
| `ACCENT` | Heraldic gold — titles, keybindings, active markers, highlights |
| `ACCENT_BG` | Selection background (dark bronze, not harsh inversion) |
| `TEXT` | Primary text in focused panes (parchment cream) |
| `TEXT_DIM` | Secondary text, unfocused pane items (faded vellum) |
| `TEXT_MUTED` | Hints, descriptions, placeholders (weathered stone) |
| `SUCCESS` / `WARNING` / `ERROR` | Heraldic tinctures: vert (sage) / amber / gules (weathered red) — never pure RGB |
| `PROMPT_BG` / `RUNNING_BG` / `SUCCESS_BG` / `ERROR_BG` | Chat block backgrounds: user prompt (warm iron), in-flight tool, tool success (dark vert), tool failure (dark gules) |

**Windows and sections** — no borders. Use `theme::section_block(title, focused)` which returns a `Block::new()` with a background fill (`SURFACE` or `SURFACE_FOCUSED`) and the title rendered inside via `.title_top()` in `ACCENT` + bold. The block has `Padding::horizontal(1)` so content is inset from the bg edge. `Block::inner()` reserves the title row, so `List`/`Paragraph` content starts below the title automatically.

**Overlays** — use `theme::overlay_block(title)` for popups (command menu, add-provider form). It fills with `OVERLAY` bg and has `Padding::uniform(1)` for breathing room. `Clear` is still rendered first to wipe underlying cells before the bg fill.

**Selection** — selection is **baked into the `ListItem`** (not via `List::highlight_style`/`highlight_symbol` or `ListState`). `list::render_list_item`/`render_list_item_line` prepend a `▶` prefix `Span` in `ACCENT` for the selected row (`  ` for unselected) and set `ListItem::style` to `Style::new().bg(ACCENT_BG).fg(TEXT)` for the selected row (so the full row width gets the `ACCENT_BG` fill, matching the old `highlight_style` behavior) or `Style::new()` for unselected. Lists are rendered statelessly via `frame.render_widget(List::new(visible), area)` — never `render_stateful_widget`. The selected index (`selected: usize`) and scroll `offset` live as plain fields on the model, mutated in `update`. Active provider/model items use `theme::active_marker(is_active)` → `●` in `ACCENT` (distinct from the selection cursor `▶`).

**Stateless widgets & scroll-into-view** — `ratatui-widgets` implements `Widget` for `&Widget` references (e.g. `&List`, `&Paragraph`, `&Block`), so widgets are rendered by reference without state. Scroll-into-view is **not** handled by a stateful widget at render time; instead the model tracks `selected`, `offset`, and `viewport_height`, and `update` calls `list::scroll_offset_for(selected, offset, viewport_height, len)` to recompute the offset whenever selection or viewport size changes. The viewport height arrives via a `Resize { viewport_height }` submodel message that `App::update` dispatches on `AppMessage::Resized { rows, cols }` (sent from the `tui.rs` event loop when the terminal size changes, computed from the popup rect + overlay block inner layout). `view` then slices the visible items with `.skip(offset).take(list_area.height)` before building the `List`. Do not introduce `ListState`/`TableState`/`ScrollbarState` for list selection — use this pattern instead.

**Scrollable text panes** — the chat history pane is the one exception to the stateless pattern: `chat::Chat` renders block-model projections into a cached `tui_scrollview::ScrollView` buffer and keeps the `ScrollViewState` in a `RefCell` (TEA `view` takes `&self` but `render_stateful_widget` needs `&mut state`); the `ScrollView` itself is also cached, rebuilt only when the content changes (`scroll_dirty`) or the pane width changes — never on every frame, so scrolling stays responsive while streaming. `Chat::update` drives scrolling (`state.scroll_up()`/`scroll_down()`, wheel = 3 rows when the cursor is inside `history_rect`) and auto-follows streaming output with `if state.is_at_bottom() { state.scroll_to_bottom() }` on token/tool/stream events. The scrollbar is drawn manually (buffer cells: `█` thumb in `ACCENT` on a `TEXT_MUTED` track) — do not use `ratatui::widgets::Scrollbar`, whose position math cannot bottom-align the thumb. Streaming is cheap by construction: committed turns are rendered as segments into a cached `committed_scroll: RefCell<ScrollView>` (rebuilt only when `committed_dirty` is set — history changed, pane width changed, diagnostics updated, or a committed block toggled), and each streaming frame re-renders only the in-flight turn's segments: when the in-flight tail's height is unchanged it is repainted in place into the cached combined buffer (stale tail rows reset first — no buffer re-allocation, no committed cell copy), and a full rebuild (fresh combined buffer + committed cell copy) happens only when the tail height changed or `committed_dirty` was set. Committed rows render through the shared view env, so `LspDiagnostics` updates mark both dirty flags. Each block projects a `Vec<Segment>` via `Block::view(width, env)` (`session/segment.rs`: `lines` + optional full-width block `bg` + `padding` inset + `hit`); the engine (`Chat::turn_segments`) stamps hit addresses (`BlockAddr { turn, block }` — tool blocks across all their segments, reasoning blocks on the header segment only), synthesizes the stateless decorations (`Block::Working` for a text-less in-flight assistant turn, `Block::ToolOnlyNote` when committed, `Block::Interrupted` on the last committed turn), and inserts transparent spacer rows between consecutive tool blocks and between turns. `Segment::measure` includes the padding rows; `Segment::view` fills the bg over full-width rows and renders the wrapped `Paragraph` into the padded rect — this is how full-width block backgrounds work (a `Line`'s bg covers only its text cells, but cell fills cover the whole rect). Hit regions are recorded into `committed_regions` (cached) + `hit_regions` (combined, content-space rows); mouse clicks hit-test via `Chat.history_rect` + the scroll offset and dispatch `BlockMessage::Toggle` to the addressed block. User prompts render as full-width `PROMPT_BG` blocks (no `You` header) with the block padding providing the blank rows and side inset. The `Sidebar` similarly caches its rendered lines and rebuilds them only when a `SidebarMessage` update arrives.

**Tool activity in the chat pane** — the agent's tool calls render as **full-width blocks** inside the same scroll view, one `ToolBlock` model per call (in `session/blocks/tool.rs`, owning name/args/status/output/stderr/expanded/worker/file_change): `RUNNING_BG` while in flight, `SUCCESS_BG` (dark green) on success, `ERROR_BG` (dark red) on failure, with a blank transparent spacer row between consecutive blocks. `ChatMessage::ToolStarted` appends a `Tool` block to the in-flight turn — structurally splitting the text stream into separate `TextBlock` chunks around it (no text offsets); `ChatMessage::ToolFinished`/`ToolOutput` flow as `BlockMessage::Tool(ToolMessage::Finish`/`Output)` into the matching running block (searched by name + worker + running status within the in-flight turn; from `Event::ToolOutput { stdout, stderr }`, produced by a per-turn forwarder task draining the `ShellOutputTx` channel; the final split streams arrive with `ToolFinished.streams: Option<ShellStreams>` captured from the tool's `ToolContext::insert_result`). Headers are human-readable per tool: `run_shell` shows the **command in bold** with the timeout (`timeout_secs` from args) and a non-zero `exit N`/`timeout Ns` label right-aligned (parsed off the persisted `exit N:` status line); `read_file` shows the **`read_file` name + path + `· lines start–end`** (exact from the tool's footer markers when present, otherwise derived from args + output length); `question` keeps its Q&A layout; worker delegations get `❖ name` + task preview; every other tool shows name + truncated args. Output renders as rows under the header — stdout in `TEXT_DIM`, stderr in `ERROR` — **collapsed by default to the last 5 lines** (stderr tail preferred for `run_shell`) with a `… +N more lines` hint; the block's `expanded` state toggles the full stdout + stderr sections. Every block ends with a timing meta row: while the call runs it shows `Elapsed 4.5s` (label in `TEXT_MUTED`, value in `ACCENT`, recomputed from the block's `started_at` wall clock on every tick — the 100 ms spinner tick keeps it live), and once finished `Took 10.3s` (`TEXT_MUTED`) from the core-measured duration carried on `Event::ToolFinished`/`Event::WorkerFinished` (`duration_ms`). Expansion is toggled by **clicking anywhere in the block** (mouse hit-testing against the recorded hit regions) or **`Ctrl+O`** (toggles the most recent tool block across turns); on finish `question` blocks default to expanded. On session load (`ChatMessage::Load`/`TurnReverted`/`TurnRestored`), tool blocks are rebuilt from `session.tool_records` (persisted in the DB), so tool activity, diffs, and split streams survive reentry (streamed tails are not persisted — the final split stdout/stderr are). Worker-delegated activity renders hierarchically: the manager's worker call is a `❖` block, and the worker's own tool blocks are separate `Tool` blocks tagged via the `worker` field. An empty assistant turn (tool-call-only reply) renders "(tool output only — no text reply)" instead of an invisible empty message; interrupted turns show an "(interrupted)" marker in `WARNING` italic. `read_file` caps each line at 2000 chars (suffix marker), defaults to 2000 lines, and appends range/footer markers; `write_file` writes atomically (temp file + rename), preserves a single UTF-8 BOM, and gates overwrites behind a read-this-turn check driven by `ReadCache.was_read` (`mode` param: `create`/`overwrite`).

**Reasoning in the chat pane** — thinking/reasoning text captured from rig's `StreamedAssistantContent::Reasoning`/`ReasoningDelta` renders as collapsible blocks that may appear anywhere in the turn — at the start, and again between/after tool calls (a new `ReasoningBlock` is created whenever a reasoning chunk follows a non-reasoning block). While chunks are streaming the header shows the spinner + `Thinking...` + a live elapsed time; once thinking ends (text/tool/context arrives, or the turn commits) `Turn::finish_thinking` flips the blocks, freezes the elapsed into the block's `duration_ms`, and the header becomes `⌥ Thought 10.3s ▸`/`⌥ Thought 10.3s ▾` in `TEXT_MUTED` italic (collapsed by default; clicking the header toggles it; the status row shows `Thinking...` while reasoning streams). Each turn owns `ReasoningBlock`s (in `session/blocks/reasoning.rs`) that accumulate their own text: `ChatMessage::ReasoningReceived` appends into the in-flight turn's trailing reasoning block (or creates one). The block's `expanded` state flips via `BlockMessage::Toggle` from a header click. Reasoning persists as positioned segments in `messages.reasoning` (`after_tool` anchor + `duration_ms` measured core-side from the segment's first→last chunk), and `build_turns` interleaves the segments among the tool records on session load, so thinking position (and duration) survive reload.

**Diff review in the chat pane** — when a tool returns a `FileChange`, it renders inside that tool's block beneath the output rows (no streaming inside the diff). `Edit { path, diff, .. }` renders a `── diff: <path>` header then each `DiffLine` with a two-column line-number gutter (`old new`, right-aligned, `TEXT_MUTED`) and a `+`/`-`/` ` marker (`SUCCESS`/`ERROR`/`TEXT_DIM`); `DiffLineKind::Ellipsis` renders as a lone `…` between hunks. `Write { path, content, .. }` renders a `── new file: <path>` header then the content with line numbers (no `+`/`-`). `Patch { files }` renders one block per file (`── diff:` / `── new file:` / `── deleted:` / `── moved: <src> → <dst>` headers). The diff is computed in `shuvarie-core` (`tools.rs::compute_diff` via `similar::TextDiff`, `grouped_ops(3)` + `iter_changes`), carried through `ToolContext::insert_result` → `FileChangeHook` → `StreamItem::ToolResult.file_change` → `Event::ToolFinished.file_change` → `BlockMessage::Tool(ToolMessage::Finish)` → `ToolBlock.file_change`. The `original`/`new` content on `FileChange` enables undo/redo of file changes (`FileChange::patch_files()` expands a multi-file patch into per-file `(path, original, new)` triples; undo writes back originals / removes added + moved-to files, redo writes new contents / removes moved-from + deleted files).

**Permission rules** — there is no interactive permission popup: tool calls either run or fail deterministically. The rules live in `crates/core/src/permissions.rs` (`resolve_read`/`resolve_write`; `~` paths expand to the home directory before any check). Read/list tools (`read_file`, `list_dir`, `grep`, `glob`) are permitted anywhere (inside or outside the workspace) except under a *hidden path* (any path component starting with `.`); the two workspace-root exceptions `.agents` and `.shuvarie` are readable and writable despite being hidden (hidden components *below* them, e.g. `.agents/.secrets/`, stay blocked). Write tools (`write_file`, `edit_file`, `apply_patch` — every hunk, including deletes and move sources) are blocked outside the working directory and under hidden paths (same two exceptions); new-file writes resolve through the first existing ancestor so the checks see the composed path. `run_shell` and `webfetch` are not path-gated. A violation surfaces as a failed tool result the model sees.

**Question prompts** — the `question` tool (M10.4) blocks the agent turn on a `QuestionGate` (`crates/core/src/question.rs`, an mpsc + `oneshot` pair): the tool sends `QuestionRequest { questions, respond }` over the question channel; the core loop assigns an id and emits `Event::QuestionAsked`; the TUI's `QuestionUI` (`src/tui/question.rs`) replaces the session text area in place (not an overlay — `SessionScreen.question` gates key routing in `map_event` and the `input_area` render slot in `view`, while the `TextArea` model is untouched, so a half-typed draft reappears when the question closes). Options list with `▶` cursor + `1..9` shortcuts, `[x]` toggles when `multiple`, a `✎ Type your own answer` row when `custom` (inline `InputBuffer` entry), per-question tabs (←/→/Tab) + a Confirm review when there are multiple questions; single-question single-select submits immediately on pick. Enter picks/toggles, Esc dismisses (`None` answers → the tool fails with "The user dismissed this question"). The user's reply flows back via `SessionEffect::AnswerQuestion { id, answers: Option<Vec<Vec<String>>> }` → `Command::AnswerQuestion`. Pending questions are invalidated (responders dropped → tool errors out) on `CancelStream`/`NewSession`/`LoadSession`; the TUI closes the prompt on those plus `Reset`/`Loaded`/`StreamError`/`StreamCancelled`. Completed `question` tool calls render as a Q&A block (`? question` / `⇒ answer` lines parsed from the persisted tool args + output; `⚠ unanswered` / `✗` markers), so they survive session reload like other tool activity.

**Context loading in the chat pane** — project context files (M7.4: workspace-root `AGENTS.md` + `.shuvarie/context/` files) surface as `◈ Loaded <path>` lines in `ACCENT` + `TEXT` at the start of the in-flight assistant turn (before tool lines), matching the tool-activity pattern. `SessionScreen` keeps `context: Vec<ContextActivity>` (paths + message index); `SessionMessage::ContextLoaded` appends entries, cleared on reset/load and on stream error/cancel alongside `tools`. Only the loaded paths render — never the file contents (they go to the agent preamble in core).

**Markdown & code highlighting** — message bodies are **not** rendered line-by-line: the text block models (`UserPrompt`/`TextBlock`/`SystemText` in `session/blocks/text.rs`) feed their content through `shuvarie_highlight::render(content)` (pulldown-cmark events → styled ratatui `Line`s) so markdown (bold/italic/code/lists/quotes/tables) and fenced code blocks render with the heraldic syntax palette from `shuvarie-highlight`'s `theme.rs`. Line feeds are **exact**: a soft break (`\n` inside a paragraph) renders as a real line break and a paragraph break (`\n\n`) renders one blank line — the renderer trims trailing blank lines so messages end cleanly. Fenced ` ```diff ` blocks use the custom `diff.rs` renderer (`+` SUCCESS, `-` ERROR, `@@` ACCENT); other fenced languages use syntect (`syntax.rs`, regex-fancy) with plain-text fallback; code-block lines get a `SURFACE` background tint. The renderer emits unwrapped lines — `Paragraph` wrapping + `line_count` still handle width. Streaming re-parses the full pending text per token, which is fine because the view is already fully rebuilt each token.

**Layout** — `App::view` renders the session screen's `view` over the full area, then any overlays (no global footer; no global title bar; branding lives in the sidebar). Each screen owns its footer row:

- `SessionScreen::view` — left sidebar (30 cols, `SURFACE` bg) + 1-cell `BG` gutter + content pane with centered title bar atop transparent chat history + input + status row, and a 1-row footer below the input. The footer shows contextual help via `theme::help_line(...)` (keybindings as styled `Span`s: keys in `ACCENT`, labels in `TEXT_MUTED`); while streaming it swaps to stop/commands hints. Session-scoped errors (`SessionMessage::ShowError`, e.g. model listing or session errors) render in the same footer row in `ERROR` instead of the help line — there is no separate global error row.

**Pane gutter** — two-pane layouts use `Layout::horizontal(...).spacing(1)` so the `BG` shows through as a 1-cell gap between panes (visual separation without borders).

**Virtual cursor** — `InputBuffer::cursor_line(text_color, cursor_color)` builds a `Line` with the character at the cursor position rendered with `Modifier::REVERSED` (the char's bg becomes the cursor color). When the cursor is past the last character, a reversed space block is appended. All text input areas (session, add-provider details) use this for cursor visualization.

**Emacs keybindings** — all text inputs support `Ctrl+B`/`Ctrl+F` (char left/right), `Alt+B`/`Alt+F` (word left/right), `Ctrl+A`/`Ctrl+E` (home/end), `Ctrl+D` (delete forward), `Ctrl+H` (backspace alias), `Ctrl+K` (kill to end). List navigations support `Ctrl+N`/`Ctrl+P` (next/prev). `Ctrl+O` toggles the most recent tool block's expanded/collapsed state. Arrow keys and physical keys remain alongside; mouse clicks toggle tool blocks and reasoning headers, and the wheel scrolls the history pane.

**Quit** — via `Ctrl+C` → `ConfirmQuit` overlay (Enter or `Ctrl+C` again to confirm, Esc to cancel). `q` no longer quits. The command menu is opened with `Ctrl+M`.

**Slash commands** — typing `/` or `:` as the first character of the message input opens an inline command tooltip (not an overlay — it renders as a floating popup above the text area inside `SessionScreen::view`, clamped to the history pane, no layout shift). The tooltip lists the shared command registry (`src/tui/commands.rs`, the same 9 `CommandEntry`s as the Ctrl+M menu, filtered by the same availability rules) with `/`-style aliases (`/model`, `/provider`, `/sessions`, `/new`, `/undo`, `/redo`, `/replay`, `/resume`, `/quit`) fuzzy-filtered by the token after the trigger. While it is open, `Tab` completes the focused command into the buffer (as `prefix + alias + space`), `↑/↓/Ctrl+N/Ctrl+P` navigate, `Esc` dismisses (re-arms when the trigger char is cleared or changed), and `Enter` runs the focused command. `/` and `:` are escaped by doubling them: `//text` / `::text` suppress the tooltip and, on submit, strip one prefix char before sending literally. On submit with the tooltip closed, a single token of the form `<trigger><alias>` (case-insensitive, no whitespace — e.g. `/undo`) parses as a command and runs instead of being sent to the model; anything else is sent as a normal message. Known commands execute as UI actions only — they are never added to the chat or sent to the LLM. `/quit` (also in the Ctrl+M menu) exits the program immediately — no confirm overlay; while a stream is active it sends `Command::CancelStream` first so the turn is marked interrupted and the core task shuts down promptly (the core loop drains buffered commands after the TUI exits, and `main` awaits it).

**Help text** — use `theme::help_line(&[("key", "label"), ...])` to render keybinding rows with keys in `ACCENT` and labels in `TEXT_MUTED`, separated by spacing. Never render help as a flat unstyled string.

When adding a new screen or widget, use the `theme` helpers — do not inline `Block::bordered()`, raw `Color` values, or `Stylize` shorthand colors.

### Launch flow

On startup `shuvarie-core` loads config + connections, opens the working-directory session store (`.shuvarie/data.db`), and — depending on the `StartupSession` param threaded into `run` — loads a session into the chat view (`SessionLoaded`): `MostRecent` for `-c`/`--current` (most recently updated session), `Session(uuid)` for `-s`/`--session <UUID>`, or `None` (default, fresh empty chat). The two flags are mutually exclusive (clap `conflicts_with`). When the TUI exits, `run_tui` returns the current session's UUID (if any) and `main` prints a hint: `shuvarie -s <SESSION UUID>` reopens the session. The TUI always opens on the **Session** route: a fresh empty chat input; submitting the first message starts a new session (the TUI sends `Command::StartSession` before `Command::SendMessage` when the screen has no session, and core's `SendMessage` handles lazy session creation — the session row (and its UUID) is created on the first message). If no providers are configured, the Session screen is shown with a **Welcome** overlay prompting the user to add a provider. Provider/model management is overlay-based (AddProvider wizard, ModelPicker) and reachable at any time via the `Ctrl+M` command menu.

user message persisted on send; assistant message row created eagerly on first tool start, updated on `Done`/`Error`/cancel with final text + reasoning + usage + interrupted flag; tool calls persisted on each `ToolResult`; most-recent session loaded on startup with tool records + reasoning reconstructed), the core task (`run`) that orchestrates provider/model listing and streaming chat (M5, M6), the eleven → twelve agent tools (`tools.rs` + `apply_patch.rs` + `todos.rs`, M7.1 + M10: read/write/edit files, `apply_patch` patch envelope, run commands, list dirs, grep, glob, `lsp`, `webfetch`, `question`, `todo` — per-item ops add/update/remove/list over a shared `TodoState` that the core task rebuilds from the session's tool records at every send, manager-only, no DB table) with deterministic permission rules (`permissions.rs`: reads blocked only under hidden paths; writes blocked outside the workspace or under hidden paths, with workspace-root `.agents`/`.shuvarie` exempt; `~` paths expand to the home directory before the check) and `compute_diff` (via `similar::TextDiff`); `edit_file` takes `edits: [{ oldText, newText }]` — all oldTexts matched against the original file (unique + non-overlapping, no-op rejected, lenient arg repair for JSON-string/single-object/legacy-flat shapes), BOM + CRLF preserved, with a fuzzy fallback (NFKC + per-line trailing-whitespace strip + smart-quote/dash/space normalization) that rewrites only touched lines so untouched lines stay byte-exact; a 500 ms interval pumps `publishDiagnostics` into `Event::LspDiagnostics`, and status changes emit `Event::LspStatus`).
- `selune` (git submodule at `vendor/selune`) is the uniform source of provider + model info: the Catwalk-format wire types (`Provider`/`Model`/`ModelOptions`/`ProviderType`), a blocking `Client` fetching a hosted catalog JSON (`CATALOG_URL` / `DEFAULT_URL`), and `embedded::all()` offline configs. Provider identity is a catalog `id` string. `shuvarie-core::catalog` loads providers (fetch with embedded fallback, bounded to 5 s at startup) and derives pricing (`estimate_cost` from `cost_per_1m_*`), context length, `requires_api_key`, and endpoint behavior from them; the AddProvider wizard and ModelPicker consume the catalog via `shuvarie-core::catalog::providers()`.
- `shuvarie-llm` streaming runs a multi-turn agent loop (`max_turns` from `config.kdl` `agent`, default `0` = unlimited) with an agent preamble supplied by the caller (the fixed orchestrator preamble plus the loaded project context, in `shuvarie-core`); `StreamItem` carries `Delta`/`Reasoning`/`ToolStart`/`ToolResult` (with `streams: Option<ShellStreams>` — display-only stdout/stderr split for `run_shell`, captured by the `FileChangeHook` from `ToolContext::insert_result` alongside `FileChange`)/`WorkerStart`/`WorkerResult`/`Done`/`Overflow`/`Error`. Reasoning content is captured from rig's `StreamedAssistantContent::Reasoning`/`ReasoningDelta` and emitted as `StreamItem::Reasoning`. A `Done` with empty text after tool calls means a tool-output-only turn. Tool errors surface as JSON error objects so the TUI marks them failed while the model still sees the message (the model-facing `run_shell` output stays combined stdout+stderr; only the display streams are split). A `ContextHook` (rig `AgentHook`) forecasts per-call input tokens anchored on the last call's real usage, mechanically trims old tool results within `[context].keep-recent-tokens`, and stops the run before a model call that would not fit even trimmed (see Context management).
- `shuvarie-lsp` owns the LSP client lifecycle: `LspManager` spawns one server per language as a `tokio::process::Command` child, wired into `async_lsp::MainLoop::run_buffered` via `tokio-util::compat`. The built-in `registry::builtin` table covers `rust-analyzer`/`gopls`/`clangd`/`pyright`/`typescript-language-server`/`zls`/`lua-language-server`/`solargraph`, probed lazily on `start` (missing binaries are skipped silently); `server <lang>` nodes in `config.kdl`'s `lsp` section override or add specs. `on_file_change` auto-starts the matching server (gated by the `lsp` `enabled` flag + per-spec `auto-start`) and sends `didChange` (full document sync). `publishDiagnostics` are collected into a per-path `DiagnosticMap` and pumped by the core task (500 ms interval) into `Event::LspDiagnostics`. The `lsp` tool exposes `start`/`stop`/`restart`/`list` (with `name` as exact id for mutations and substring filter for `list`, plus `all` to list configured-not-running servers) and `analyze` (with a `path` — file or directory, defaulting to the workspace root — that starts the matching server if needed, opens the target file(s), and returns the published diagnostics).
- `shuvarie-core::skills` implements the skills system: `Skills::load` scans the workspace `.agents/skills/`, the global `~/.config/shuvarie/skills/`, and any `[skills] dirs` for `SKILL.md` files, parsing their YAML front-matter (`name`, `description`, `metadata.category`, `metadata.tags`) via `yaml_serde` (workspace skills win over global on name collision). Skills load at core-task startup and emit `Event::SkillsLoaded`; the sidebar Skills panel renders name + description per skill. The agent preamble lists available skills (name + description + path) so the agent can `read_file` a skill's `SKILL.md` when relevant. `[skills] enabled` (default true) gates the system. Deferred follow-ups: per-skill enable/disable toggles, skill content injection into the preamble (currently only names/descriptions/paths are listed), and a skills management UI.
- Diff review (M7+): `shuvarie-core`'s file tools implement `rig::tool::Tool` and attach a `FileChange` (`Edit { path, diff, original, new }` computed via `similar::TextDiff`, or `Write { path, content, original }`) to their `ToolContext` via `insert_result`; a `FileChangeHook` (rig `AgentHook`) captures it and forwards it through `StreamItem::ToolResult.file_change` → `Event::ToolFinished.file_change` → the TUI's inline diff renderer (line-number gutter + `…` ellipsis between hunks). The `original`/`new` content enables undo/redo of file changes. File access follows the deterministic permission rules in `shuvarie-core::permissions` (see Permission rules above) — violations surface as failed tool results, not prompts.
- Multi-agent orchestration (M7.3): the main agent is an always-active orchestrator; `shuvarie-core::agents` builds three `WorkerAgent`s (`explore_workspace`, `run_tests`, `edit_files`) per `SendMessage`, each running its own `run_worker` loop (`worker_max_turns` from `config.kdl` `agent`, default `0` = unlimited) over a narrowed tool set with a role-specific preamble. Worker activity flows back through an mpsc channel per worker, merged with the manager's rig stream via `select_all` (`merge_streams` in `provider.rs`); the `worker` field on `ToolStart`/`ToolResult` tags nested activity for hierarchical TUI rendering (`❖` delegate marker, indented sub-tool lines). Worker usage accumulates into a shared `TokenUsage` folded into the session totals on `Done`.
- Cost estimates in the sidebar Context panel are computed by `shuvarie-core::catalog::estimate_cost` (per-model rates from the `selune` catalog, first-model fallback for unknown ids); token counts are real `Usage` data. User-configurable rate overrides land later.
- LSP sidebar panel shows real server status (running servers with `✓`/`⟳`/`✗` markers + per-server diagnostic counts; "no servers" / "disabled" placeholders when idle). The Skills sidebar panel shows the loaded skills (name + description per skill; "none" placeholder when empty), driven by `Event::SkillsLoaded`.
- History search (M7.5/M7.6) is hybrid BM25 + semantic (`Ctrl+R` overlay, RRF-merged); deferred follow-ups: token-based chunking for long messages (8 KB cap), query-term highlighting in results, and injecting retrieved hits into the agent preamble.
- Model search uses `nucleo` (fuzzy matcher) via `src/tui/search.rs`; the Ctrl+M command menu (`src/tui/command_menu.rs`) and the inline slash command tooltip (`src/tui/slash.rs`) share the command registry in `src/tui/commands.rs` (actions, entries, slash aliases, trigger/escape parsing).
